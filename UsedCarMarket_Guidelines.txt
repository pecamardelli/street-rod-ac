STREET ROD MANAGER – USED CAR MARKET SYSTEM GUIDELINES

PURPOSE
This document defines the official guidelines for the used car market system in Street Rod Manager.
Its goal is to provide a robust, gameplay-oriented market that respects catalog boundaries and maintains architectural separation between AC content and game state.

The used car market is a gameplay overlay on top of the immutable content catalog.

CORE PHILOSOPHY
- CarProfile stores gameplay data, not CarDefinition
- Market spawning is deterministic and logged
- Condition affects actual car performance
- Multiple dealers create market diversity
- Daily refresh creates dynamic economy
- Never modify AC installation directories

ARCHITECTURAL LAYERS
The used car system follows a four-layer architecture:

1. CarDefinition (Catalog) - Immutable AC identity from import
2. CarProfile (Catalog) - Mutable gameplay properties (price, precedence)
3. UsedCarListing (Market State) - Cars currently for sale
4. CarInstance (Player State) - Cars owned by player

Each layer references the previous by stable ID.
Lower layers never modify higher layers.

CAR PROFILE SYSTEM
CarProfile represents gameplay interpretation of a car.

Storage:
- Lives in catalog.db (same as CarDefinitions)
- Separate collection: catalog_carprofiles
- One profile per CarDefinition (1:1 relationship)
- Never stored in AC installation directories

Required properties:
- CarDefinitionId (references CarDefinition.Id)
- BasePrice (decimal)
- DealerPrecedence (float, 0.0 to 1.0)
- CreatedDate, LastUpdatedDate
- DataSource (Generated, Manual, Imported)

Optional future properties:
- StreetRodEra
- PerformanceTier
- IsStreetLegal

Rules:
- Profiles are created on first import if missing
- Profiles persist across AC content updates
- Profiles can be manually edited (future feature)
- Profiles can be shared as data packs (future feature)

PROFILE GENERATION
Every CarDefinition must have a CarProfile.

Default generation strategy:
- Calculate BasePrice from power/weight ratio
- Calculate DealerPrecedence from year, brand, source
- Mark as DataSource.Generated
- Log profile creation

Generation occurs:
- During initial import (if profile missing)
- On demand when profile not found
- Never overwrites existing profiles

PRICING ALGORITHM
BasePrice is calculated from car specifications.

Primary factors:
- Power/weight ratio (primary metric)
- Year (older = cheaper, classics = premium)
- Brand reputation (Ferrari > Ford)
- Content source (Kunos = quality = higher)

Formula (starting point):
- Base = (BHP / Weight_kg) × 1000
- Adjust for year (1960s discount, 2000s premium)
- Adjust for brand (luxury multiplier)
- Adjust for source (Kunos/DLC × 1.2)
- Clamp to reasonable range ($5,000 - $500,000)

Pricing must be logged during generation.

DEALER PRECEDENCE SYSTEM
DealerPrecedence controls spawn probability (0.0 = rare, 1.0 = common).

Factors affecting precedence:
- Year: Recent cars = higher precedence
- Source: Kunos cars = higher precedence
- Brand: Common brands = higher precedence
- Performance: Exotic cars = lower precedence

Formula guidelines:
- Common street cars: 0.7 - 1.0
- Performance cars: 0.4 - 0.6
- Exotic/rare cars: 0.1 - 0.3
- Race-only cars: 0.0 - 0.2

Lower precedence = fewer spawns = rarer in market.

USED CAR LISTING STRUCTURE
UsedCarListing represents a car for sale.

Required properties:
- string CarDefinitionId (references Catalog)
- decimal Price (varies from BasePrice)
- int Mileage
- float Condition (0.0 = broken, 1.0 = perfect)
- string SkinId (which visual variant)
- DateTime ListedDate
- string DealerLocation
- bool IsSold

Rules:
- Multiple listings per CarDefinition allowed
- Each listing has different skin and condition
- Listings stored in GameState.UsedCars
- Sold listings remain in state (for history)
- Never embed full CarDefinition data

MARKET SPAWNING LOGIC
New listings spawn based on precedence.

Spawning rules:
- Higher precedence = more instances per model
- Lower precedence = fewer instances (sometimes zero)
- Each instance gets random skin from available skins
- Each instance gets random condition (0.3 - 0.95)
- Price varies ±20% from BasePrice based on condition
- Better condition = higher price

Spawn calculation:
- Roll random for each CarDefinition
- If random < DealerPrecedence: spawn 1-3 instances
- Number of instances weighted by precedence
- Each instance assigned to random dealer location

All spawns must be logged with structured properties.

MARKET SIZE STRATEGY
Market contains multiple instances of same model.

Rules:
- Common cars (precedence > 0.7): 1-3 listings
- Performance cars (0.4-0.6): 0-2 listings
- Exotic cars (< 0.3): 0-1 listing
- Total market size: 30-50 active listings
- Distributed across multiple dealers

Variety requirements:
- Different skins per instance
- Different conditions per instance
- Different prices based on condition
- Different dealer locations

REFRESH TIMING
Market refreshes daily (in-game time).

Refresh rules:
- Triggered when GameState.Date advances
- Remove old sold listings (older than 7 days)
- Despawn unsold listings (older than 14 days)
- Spawn new listings based on precedence
- Log refresh operation with before/after counts

Refresh must:
- Be deterministic (same seed = same market)
- Preserve player-relevant listings
- Maintain market size targets
- Log all operations

DEALER LOCATION SYSTEM
Market supports multiple dealer locations.

Location properties:
- Name (e.g., "Downtown Motors", "Eastside Garage")
- Region (e.g., "Downtown", "Industrial", "Suburbs")
- Specialization (optional: "Imports", "Classics", "Performance")

Listing assignment:
- Each listing assigned to one dealer
- Distribution roughly equal across dealers
- Specialization affects spawn weights (future)

Player experience:
- Can filter by dealer location
- Can visit specific dealers
- Each dealer has distinct inventory

CONDITION IMPACT ON PERFORMANCE
Condition directly affects car performance.

Condition scale:
- 1.0 = Perfect (100% power)
- 0.7 = Good (85% power)
- 0.5 = Fair (70% power)
- 0.3 = Poor (50% power)

Performance modification:
- Read car's data/power.lut file
- Scale power curve by condition factor
- Write modified curve to temporary location
- AC loads modified curve at race time
- Never modify original AC installation files

Implementation requirements:
- Copy car data folder to temporary location
- Modify power.lut in temporary copy
- Point AC to temporary car folder
- Clean up temporary files after race
- Log all power.lut modifications

Rules:
- Original AC files remain untouched
- Modifications are per-instance, not per-definition
- Player can repair cars to restore condition
- Better condition = better performance = higher value

TRANSACTION FLOW
Purchasing a car requires confirmation.

Purchase steps:
1. Player selects UsedCarListing from UI
2. ViewModel validates availability and funds
3. Show confirmation dialog with:
   - Car name, brand, year
   - Price
   - Condition and mileage
   - Dealer location
4. If confirmed:
   - Create CarInstance from listing
   - Add to GameState.Player.Cars
   - Deduct money from player
   - Mark listing as IsSold = true
   - Save GameState
   - Log purchase with structured properties
5. Navigate back to game screen
6. Show success message (optional)

Transaction must be atomic:
- All changes succeed or all fail
- Never partial transactions
- Log failures with sufficient context

Error handling:
- Insufficient funds: show dialog, don't deduct money
- Listing already sold: refresh market, show error
- Save failure: rollback transaction, show error
- All errors logged with structured properties

DATA FLOW SUMMARY
End-to-end flow:

Import → Profile:
1. CarDefinition imported from AC
2. CarProfile created (if missing)
3. Both stored in catalog.db

Spawn → Listing:
1. Daily refresh triggered
2. Read CarDefinitions (status = Active)
3. Read CarProfiles for pricing/precedence
4. Generate UsedCarListings
5. Store in GameState.UsedCars
6. Log spawn operation

Display → UI:
1. ViewModel reads GameState.UsedCars
2. For each listing, query CarDefinition from catalog
3. Query CarProfile for base info
4. Combine into UsedCarListingViewModel
5. Resolve badge images from cache
6. Bind to UI

Purchase → Instance:
1. Player confirms purchase
2. Validate funds and availability
3. Create CarInstance from listing
4. Add to GameState.Player.Cars
5. Mark listing as sold
6. Deduct money
7. Save GameState
8. Log transaction

Race → Performance:
1. Player selects owned CarInstance
2. Query CarDefinition for AC folder
3. Copy data folder to temp location
4. Modify power.lut based on condition
5. Launch AC with temp folder
6. Clean up after race

PERSISTENCE STRATEGY
Data storage locations:

catalog.db:
- CarDefinition (imported identity)
- CarProfile (gameplay properties)

saves/{savename}.db:
- GameState.UsedCars (market listings)
- GameState.Player.Cars (owned instances)

Cache:
- Badge images
- Skin preview images

Temporary (race-time only):
- Modified car data folders
- Scaled power.lut files

Rules:
- Never write to AC installation
- Temporary files cleaned up after use
- Save files remain valid if catalog changes
- Legacy car handling (missing from catalog)

USED CAR MARKET SCREEN
Screen responsibilities:
- Display available listings grouped by dealer
- Show car details (name, brand, year, price, condition)
- Show badge images and skin previews
- Filter by dealer, price range, condition
- Sort by price, condition, mileage
- Handle purchase command
- Show confirmation dialog
- Navigate back to game screen

ViewModel pattern:
- UsedCarMarketScreenViewModel
- Commands: PurchaseCarCommand, FilterCommand, BackCommand
- Observable collections for listings
- Read-only projections (never modifies catalog)
- Logs navigation and purchases

Screen integration:
- Accessed from "Newspaper" button (used car ads)
- Follows existing screen patterns
- Animations (fade in, slide up)
- Back button navigation
- Error dialogs for failed purchases

SERVICES ARCHITECTURE
Required services:

ICarProfileRepository:
- GetProfile(carDefinitionId)
- UpsertProfile(profile)
- GetOrCreateProfile(carDefinitionId)
- GetAllProfiles()

ICarProfileService:
- GenerateDefaultProfile(carDefinition)
- CalculateBasePrice(carDefinition)
- CalculatePrecedence(carDefinition)

IUsedCarMarketService:
- SpawnListings(gameState, dealers)
- RefreshMarket(gameState)
- PurchaseCar(gameState, listing) → CarInstance
- GetAvailableListings(gameState, dealerFilter?)

ICarPerformanceService:
- CreateTempCarData(carInstance, carDefinition)
- ScalePowerCurve(powerLutPath, condition)
- CleanupTempFiles()

All services must:
- Be injected, not static
- Use structured logging
- Handle errors gracefully
- Return results, not throw exceptions
- Be testable

LOGGING REQUIREMENTS
All operations must be logged.

Required log events:
- Profile generation (Debug)
- Market spawn (Information)
- Market refresh (Information)
- Purchase transactions (Information)
- Performance modifications (Debug)
- Errors and failures (Warning/Error)

Structured properties:
- {CarId}
- {CarDefinitionId}
- {Price}
- {Condition}
- {DealerLocation}
- {ListingCount}

Log categories:
- Market
- Transaction
- Performance

ANTI-PATTERNS (FORBIDDEN)
- Writing custom_data.json to AC folders
- Modifying AC installation files permanently
- Embedding CarDefinition in UsedCarListing
- Modifying CarDefinition from market operations
- Deleting catalog entries when cars are sold
- Static/global market state
- UI reading AC files directly
- Spawning without precedence consideration
- Transactions without confirmation
- Silent failures

MENTAL MODEL SUMMARY
- CarProfile is gameplay interpretation, not AC data
- Market is dynamic overlay on static catalog
- Condition affects real performance, not just display
- Precedence controls rarity and market presence
- Multiple dealers create exploration gameplay
- Daily refresh creates living economy
- Purchases are permanent (CarInstance creation)
- Everything is logged for diagnostics

These rules are intentional constraints.
They exist to maintain clean separation between imported content and gameplay state while creating engaging market dynamics.
