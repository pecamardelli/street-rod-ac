STREET ROD MANAGER – LOGGING SYSTEM GUIDELINES

PURPOSE
This document defines the official logging strategy for the Street Rod Manager project.
Its goal is to ensure consistent, structured, and useful logging across the entire application while preventing logging from becoming a source of architectural decay or UI coupling.

Logging exists for developers and diagnostics, not for users.

CORE PHILOSOPHY
- Logging is an infrastructure concern
- Logging must never drive application logic
- Logs are structured data, not free-form text
- Logging must be centralized and consistent
- Logging must be safe, non-blocking, and low overhead

LOGGING ENGINE
The project uses a dedicated logging engine internally.

Rules:
- The logging engine must be wrapped behind an application-level abstraction
- Application code must never depend directly on the logging engine
- The engine may be replaced without affecting application logic

LOGGING ABSTRACTION (MANDATORY)
All logging must go through a project-defined logging interface.

Rules:
- No direct calls to third-party logging APIs outside the logging infrastructure
- No static global logger usage scattered across the codebase
- Logging is injected where needed

This prevents tight coupling and inconsistent usage.

CATEGORIES & CONTEXT
Every log entry must include a category.

Recommended categories:
- App
- Startup
- Import
- Catalog
- Save
- ACIntegration
- UI
- Navigation
- Dialog
- Performance
- Diagnostics

Categories must be stable and intentional.

STRUCTURED LOGGING
Logs must be structured.

Rules:
- Use named properties instead of string concatenation
- Log events, not prose
- Include relevant identifiers (CarId, TrackId, SaveId, SessionId)

Structured logging is mandatory for import, save, and AC integration systems.

LOG LEVELS
Use log levels consistently.

Recommended semantics:
- Debug: Detailed technical flow (disabled by default)
- Information: High-level lifecycle events
- Warning: Recoverable issues
- Error: Failed operations
- Critical: Application-threatening failures

Do not misuse levels for convenience.

WHAT MUST BE LOGGED
The following events must always be logged:
- Application startup and shutdown
- Import start and completion
- Import failures and skipped content
- Rescan operations
- Save load and save failures
- Detection of legacy or broken content
- Unexpected exceptions

WHAT SHOULD BE LOGGED (DEBUG ONLY)
- File enumeration
- Metadata parsing details
- Enrichment steps
- Performance measurements

WHAT MUST NOT BE LOGGED
- UI rendering events
- Per-frame or high-frequency UI actions
- Large binary data
- Full file contents
- Sensitive user information

ERROR HANDLING RULE
Every caught exception must follow one of these rules:
- Logged with sufficient context
- Explicitly ignored with a documented reason

Silent failures are forbidden.

LOG OUTPUT STRATEGY
Logs must be written to persistent storage.

Rules:
- Rolling file logs
- One primary log stream
- Optional specialized logs (import, crash)
- Log retention policy must exist

Logs must never be written into:
- Assetto Corsa installation directories
- Game content folders

USER EXPERIENCE SEPARATION
Logging and user-facing messaging are separate concerns.

Rules:
- Logs are technical and verbose
- UI messages are friendly and minimal
- Log messages must never be shown directly to users

The UI may summarize outcomes, but never expose raw logs.

PERFORMANCE & SAFETY
Logging must:
- Be asynchronous
- Never block the UI thread
- Fail gracefully if logging infrastructure fails

Logging must never crash the application.

ANTI-PATTERNS (FORBIDDEN)
- Direct logging engine usage in application code
- Static global logger access
- Logging inside rendering loops
- Logging as a substitute for error handling
- Swallowing exceptions without logging

MENTAL MODEL SUMMARY
- Logging is a passive observer
- Logs describe what happened, not what to do
- The application must function correctly even if logging fails
- Logs exist to diagnose, not to control

These rules are intentional constraints.
They exist to ensure diagnostics remain reliable, actionable, and non-invasive.
